SECTION 01 · 01

Why automation choices matter

Engineering teams do not lack ideas for scripts. They lack time to build, test, explain, and maintain every idea. The hard part is choosing the right problem.

A small automation can save a few minutes many times. A poorly chosen automation can create a second job: fixing broken rules, explaining strange outputs, and checking work that used to be simple. Think of automation like a power tool. It helps most when the material and the cut are understood.

The best first automation is not the most impressive one. It is the one that reliably removes real friction.

For ship-piping design, possible candidates include producing a valve list, checking required columns in an export, formatting a support summary, or creating a repeatable drawing setup. A design judgment about whether a support is structurally suitable is different. That judgment needs engineering intent, evidence, and accountability.

Start with a task people already understand. Make its steps visible. Then decide whether software should do all of it, part of it, or none of it.

A useful question is: “If this task disappeared tomorrow, what problem would the team notice?” If the answer is unclear, the task may not deserve a custom tool yet. If the team immediately names repeated delays or rework, you have a reason to investigate.

Automation should give people more room for careful engineering, not make the work harder to understand. Keep the original process documented so that the team can still operate when the script is unavailable.

Also count the full cost. A script may save time during each run but require updates whenever a source file or application changes. Think of the first build as buying a tool; testing, documentation, and maintenance are the cost of keeping it useful.

SECTION 02 · 02

What does “automation” mean?

Plain definition

Automation is using a tool or system to perform a repeatable part of a task with less manual effort.

It may be a small Excel formula, a ZWCAD LISP command, a PowerShell script, a Python utility, or a larger workflow between systems.

Three levels

  • Assist: prepare information for a person.
  • Automate a step: perform one clear repeatable action.
  • Automate a workflow: connect several steps with checks and recovery.

Automation is not the same as removing people. A good workflow often handles predictable steps and gives people clear choices when a case is unusual. Like a spell-checker, it can catch common patterns without deciding what the writer truly meant.

A useful process description answers five questions: What starts the work? What information is needed? Which rules are applied? What result should appear? What happens when something is missing or unexpected? If these answers are not agreed, the process is not ready for full automation.

For example, “create a valve list” is too broad. “Read the approved export, verify required fields, group valves by the agreed key, write a dated spreadsheet, and report invalid rows” is much easier to build and test.

Common misunderstanding

“If I can automate it, I should.” Not necessarily. A task that happens rarely, changes constantly, or depends on unclear judgment may cost more to automate than to perform manually.

Another useful distinction is between a task and a decision. A task might sort a list by an approved rule. A decision might determine whether a support arrangement is suitable for the design. Software can prepare evidence for the decision, but the responsible engineer still needs to own the judgment.

Automation also has levels. A formula that flags a missing value may be enough. A script that generates a complete report may be appropriate later. Begin with the smallest change that solves the real problem.

SECTION 03 · 03

The opportunity framework

Use these four components as a filter. They are meant to work together, like four checks before releasing a drawing.

Look for repeated effort, waiting, rework, avoidable mistakes, or a risk that matters. Estimate how often the task happens and what it costs.

Example: A valve list is rebuilt for every delivery. The repeated effort makes it worth investigating.

Identify the trigger, inputs, rules, outputs, exceptions, and owner. If two experienced people use different rules, agree on the process before encoding it.

Example: A pipe summary needs a written rule for grouping by line number and nominal size.

Check file formats, permissions, application interfaces, data quality, dependencies, and skill available. A technically possible task may still be expensive to maintain.

Example: An Excel export may be easier to process than scraping changing screen positions.

Define validation, logs, backups, permissions, human review, and a manual fallback. The more serious an error would be, the stronger these controls must be.

Example: A script flags a missing column and stops instead of generating an incomplete deliverable.

Follow the learning loop: Value · Clarity · Feasibility · Control.

Quick check

What makes a framework useful?

A framework helps compare different tasks using the same questions.

The components also constrain one another. A task may have high value but poor clarity, so the next action is to standardize the rule. A task may be clear and valuable but impossible to access safely with the available permissions, so feasibility becomes the blocker. A task may be technically easy but difficult to recover from, so control becomes the blocker.

Write down the weakest component before you choose a tool. That weakness tells you what to fix first and gives the team a reason for delaying, narrowing, or rejecting the automation.

SECTION 04 · 04

How the parts work together

These checks are not four separate scores to admire. They form a sequence that reduces uncertainty.

01
Observe the current work

Write down what triggers it, who does each step, which data is used, and where delays occur.

↓
02
Make the rules explicit

Agree on required fields, naming rules, acceptable outputs, and cases that need a person.

↓
03
Build the smallest useful change

Automate one stable part, rather than trying to rebuild the whole department's workflow at once.

↓
04
Test, compare, and maintain

Compare results with the baseline, record failures, assign an owner, and update the rules when the process changes.

Important distinction

Automation follows rules; it does not make unclear rules correct. If the input is unreliable, validate or improve it before trusting the output.

The four checks can also reveal that only part of a task should be automated. For example, a report can be generated automatically while unusual rows are sent to a reviewer. This is often safer than forcing every case through one rigid path.

Think of the framework as a gate, not a competition. A high value score cannot compensate for an unsafe failure mode. A technically easy script is still a poor choice if nobody can explain or verify its output.

Value asks whether the task deserves attention. Clarity asks whether the rule is stable. Feasibility asks whether the chosen tools can perform the work reliably. Control asks whether people can trust, check, and recover from the result. Together, these checks prevent the team from confusing “possible to build” with “worth maintaining.”

Imagine choosing a route through a shipyard. The shortest route is not automatically the best if it crosses a restricted area. In the same way, a fast automation path is not acceptable if it bypasses a review or creates a risk the team cannot manage.

SECTION 05 · 05

How to choose and start

Use these six steps on one task. Each step produces something you can show another person.

1

Write the task as a result

Describe the start, input, output, and finish condition. Avoid vague goals such as “make Excel better.”

↳ Applies: Clarity
2

Measure the current process

Record frequency, minutes per run, error types, rework, and waiting time. Use a few real examples, not memory alone.

↳ Applies: Value
3

Remove needless steps

Standardize naming, fields, and handoffs first. Do not automate a workaround that can be removed.

↳ Applies: Clarity
4

Choose the simplest tool

Use a built-in feature when it fits. Choose LISP for drawing commands, Excel formulas for sheet logic, PowerShell for file tasks, or Python for broader data handling.

↳ Applies: Feasibility
5

Test normal and unusual cases

Use copied data or a test drawing. Include missing fields, unexpected formats, duplicates, and cancellation where relevant.

↳ Applies: Control
6

Release with a fallback

Document how to run it, how to spot failure, who owns changes, and how to return to the manual process.

↳ Applies: Control
Release gate

Before routine use, have another person run the documented steps, confirm the expected output, and explain what to do after a failure. If only the author can operate or repair the automation, the handoff is not complete.

Keep the first version narrow. If a task includes ten steps, you may only need to automate the two most repetitive ones. A partial solution can still be valuable when it leaves a clear handoff for the steps that need human judgment.

Finally, name a maintenance owner. That person does not have to write every line, but they should know where the files are, what the script expects, how to test a change, and when to stop using it.

SECTION 06 · 06

Benefits and trade-offs

When it is a good fit

  • More capacityPeople spend less time repeating the same steps.
  • More consistencyOne agreed rule is applied in the same way.
  • Earlier detectionChecks catch missing fields before delivery.
  • Better traceabilityLogs make it easier to explain what happened.

When it is a poor fit

  • Fragile maintenanceSmall source changes break the workflow.
  • Hidden errorsWrong inputs produce confident-looking wrong outputs.
  • Lost judgmentPeople trust an output without reviewing its meaning.
  • Single-person dependencyNo one else knows how to support the script.

The goal is not the largest number of automated tasks. The goal is a healthier process with dependable output and less wasted effort.

Compare benefits with the whole lifecycle, not just the first successful run. A tiny macro with a clear owner may be better than a complex tool that depends on fragile screen positions, special permissions, or one person's memory.

Also consider who will be affected. Ask the people doing the work whether the new process makes the task clearer, whether it creates extra checks, and whether they know how to report a problem. Adoption is part of quality, not an optional extra.

Which is an outcome rather than an activity?

Measure the effect on work, not how busy the build looked.

SECTION 07 · 07

Three short workplace scenes

WRONG WAY

“Just automate everything”

Engineer: “I'll make a script that changes every drawing automatically.”

Reviewer: “What if the drawing uses a different unit or layer rule?”

Engineer: “I haven't checked those cases yet.”

The plan skipped Control and treated every drawing as identical.

RIGHT WAY

“Start with a safe subset”

Engineer: “I'll test the naming command on copied drawings from three known cases.”

Reviewer: “How will we know it worked?”

Engineer: “I'll compare the names, check the log, and keep the manual method available.”

The engineer applies Control before widening the scope.

RIGHT WAY

“Make the rule visible”

Engineer: “The pipe summary groups by line number and size.”

Teammate: “What happens when the size is blank?”

Engineer: “It flags the row for review instead of guessing.”

The workflow makes Clarity and Control visible.

Notice the difference between the scenes. The wrong-way plan treats the tool as the solution before the process is understood. The right-way plans make assumptions visible, test small, and keep a person responsible for unusual cases.

In a real team, invite the people who perform the task to review the process map. They often know about exceptions that a developer cannot see from a sample file alone. That conversation can prevent weeks of avoidable rework.

A good release is not the moment the code runs once. It is the moment another person can use it safely, recognize a bad result, and recover without guessing.

Before launch, ask a teammate to deliberately try one invalid input. Watch what the workflow does. If it fails silently, gives an unclear message, or leaves a half-written file, the test has found a real improvement opportunity.

After the pilot, ask what changed for the person doing the work. A faster script is not enough if the new process makes review harder or creates more confusion about ownership.

SECTION 08 · 08

Real-world examples and opportunity scorecard

These examples are patterns you can adapt, not promises that every setup will work the same way. Start by confirming your actual inputs and application limits.

EXAMPLE 01 · CAD

Repeatable drawing setup

Candidate: Apply a known layer, text, or naming standard to selected objects.

First check: Units, object types, current selection, and undo behavior.

Human role: Review the drawing's engineering meaning and approve the final output.

EXAMPLE 02 · DATA

Excel to CSV summary

Candidate: Export a validated table to a consistent CSV for another workflow.

First check: Required columns, blanks, duplicates, encoding, and decimal formats.

Human role: Resolve conflicting data and approve the released summary.

EXAMPLE 03 · REPORTING

Pipe-support or valve list

Candidate: Generate a standard report from a stable export and approved grouping rules.

First check: Source version, row counts, units, and missing attributes.

Human role: Confirm that the report matches the design and delivery requirements.

These are illustrative ratings, not measured company data. Change the ratings to reflect your actual workflow before using the comparison to prioritize work.

For a fair comparison, rate candidate tasks using the same rules. A stable report may score well because it happens often and has clear outputs. A one-off task may score poorly because the build and maintenance cost cannot be spread across many runs. A high-impact design judgment can still be a poor full-automation candidate if the rules are unclear or the failure cost is high.

Use the scorecard to choose what to investigate first, not to approve unattended operation. Before building, ask the process owner to confirm the rules and ask a reviewer to agree on what a correct result looks like.

CAD example: a command that applies an agreed naming pattern may be a sensible first pilot. Confirm the selection behavior, how the command handles locked or unsupported objects, and whether the user can undo the change.

Data example: a CSV exporter should verify the expected headers and row count before releasing its file. If a required field is missing, it should create a clear warning or stop. It should not silently fill the gap with a guess.

Reporting example: a valve list generator should preserve the source, record the export date, and flag rows that cannot be grouped by the agreed rule. A reviewer can then resolve exceptions without rechecking every normal row manually.

For all three examples, keep a small test pack: one normal case, one missing-data case, one unexpected-format case, and one case that should be rejected. Save the expected result alongside the test data. This makes later changes easier to verify.

Consider the tool fit as well. A simple spreadsheet formula is often enough for a local calculation. A LISP routine fits repeated drawing commands inside ZWCAD. PowerShell is useful for predictable file and folder operations. Python can help when the task needs richer data handling, multiple files, or a small user interface.

Do not choose by popularity alone. Check whether the tool can read the required inputs, whether it is permitted in your work environment, and whether another person can support it. A tool that is already approved and understood may beat a more powerful option that adds setup and maintenance burden.

Finally, separate the automation from the engineering approval. The tool can prepare a list, highlight missing attributes, and create a traceable report. The accountable engineer still checks whether the information is correct for the design and delivery.

SECTION 09 · 09

The whole guide in one sentence

Automate the stable, repeated parts of a valuable process only after its rules are clear, its results can be checked, and a person can recover from failure.
